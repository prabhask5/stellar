# Decisions

One line of context, the choice, and why. Newest at the bottom of each phase.

## Phase 0 — Scaffold

- **TypeScript version.** TypeScript 7 is the latest release, but `typescript-eslint` only supports `<6.1`. → Pinned TypeScript `~6.0`. Linting with type-aware tooling matters more than the newest compiler.
- **Package manager.** pnpm 12 via Corepack (`packageManager` field). Native build scripts are allow-listed in `pnpm-workspace.yaml`.
- **Internal packages ship TypeScript source.** `packages/*` export `./src/*.ts` directly and are transpiled by Next (`transpilePackages`) and Vite (WXT). No per-package build step, so edits are instant and there is one compiler configuration.
- **Token outputs are committed.** `packages/ui-tokens/css/*.css` and `docs/ios/StellarTokens.swift` are generated by `pnpm tokens` and checked in; a unit test fails when they drift from `tokens.json`. Builds never depend on a generation step.
- **Tailwind names.** `text.primary`/`text.secondary` map to `fg`/`fg-2`, `bg.void` to `void`, `glass.border` to `hairline`, so utilities read naturally (`text-fg-2`, `border-hairline`).
- **Safe-area variables.** Components read `--sat/--sar/--sab/--sal`, which are defined only as `env(safe-area-inset-*)`. Tests simulate a notch or Dynamic Island by adding a class to `<html>` (SPEC §9.1 allows a test-only class). No inset value is hardcoded in components.
- **CSS starfield.** Stars are seeded radial-gradient tiles rendered by a server component: zero client JS, identical on every device, part of first paint.
- **Playwright runs against the standalone build** (the same artefact the Docker image runs), with Chromium using iPhone device descriptors for the phone projects. WebKit is not required to run the suite.

## Phase 1 — Database

- **Local test stack.** SQL parity tests and e2e need a real Supabase. `dev/supabase/docker-compose.yml` runs a lean compatible stack (Postgres 15 + GoTrue + PostgREST + Realtime + pg-meta behind an nginx gateway on :54321) instead of the full Supabase distribution: same APIs, a fraction of the disk and start-up time. Dev-only keys live in `dev/supabase/dev.env`.
- **Idempotent migrations.** Every migration is written so it can be re-run (`create … if not exists`, `create or replace`, `drop … if exists`). That makes the paste-into-Studio fallback safe to run twice and lets the runner, the pg-meta path and the pasted script share one SQL source. SQL is embedded in `bundle.generated.ts` so the standalone server never reads migration files at runtime.
- **`sort_order` is `double precision`.** Reorders write one row with the midpoint of its neighbours; `sp_rebalance` respaces a list when a gap is exhausted. Chosen over text keys because inserts without a rank (API clients) get one from a one-line trigger, and ordering has no collation pitfalls.
- **Timer extras.** `sp_focus_state` adds `phase_total_ms` (the planned length, fixed when a phase starts, so every device draws the same ring even if settings change mid-phase) and `last_completed_phase` / `last_completed_at`. The scheduler compares `last_completed_at` with `notified_phase_end_at` to send each phase-end push exactly once, whichever device advanced the timer.
- **Timer semantics where the spec is silent.** After a long break the round resets to 1. `skip` follows the same auto-start rule as a natural phase end. An advancer up to 10s late starts the next phase exactly at the boundary (no drift); later than that, from "now" (no stale catch-up chain after downtime). `end` and `skip` record an abandoned phase with the time actually spent.
- **Timer state is written only by RPC.** `sp_focus_state` and `sp_focus_sessions` are select-only for the owner; `sp_timer_action` (security definer) is the single writer, so the version check cannot be bypassed.
- **Ledger rule.** Only un-completing something appends negative points. Structural changes (deleting a task, list or routine, rewriting a routine) never touch the ledger: earned stardust is permanent (pillar 3). Two derived awards are reconciled as state: "goal list 100%" and "routine day 100%" are reversed when the state stops being true and are never awarded twice.
- **Goal progress points telescope.** Points are `round(50·new) − round(50·old)`, so one hundred 1% steps earn exactly the same 50 as one jump.
- **Routines hard-delete; tombstones cover delta sync.** Deleting a routine removes its logs (spec). Hard deletes (routines, logs, block sites, quotes) write `sp_tombstones` so `updated_since` can report removed ids. `sp_routines.deleted_at` exists per the spec but is unused. Task/goal/block lists and tasks/goals soft-delete; deleting a list soft-deletes its children with the same timestamp so Undo restores exactly those.
- **Clients compute, Postgres decides.** The web app keeps routines + logs in its cache and uses the shared TypeScript functions for instant rings and streaks; the SQL twins (`sp_routine_days`, `sp_routine_streak`, `sp__scheduled`) serve the API and are held to the same fixtures.
- **Era numbering.** Eras are shown one-based ("Era III · Nebula"), matching the mockup.
- **Quotes.** 132 built-ins, all from authors or translations in the public domain, attributed; commonly misattributed lines were left out.
- **Streak definition.** Consecutive _scheduled_ days completed, counting back from today; an unfinished today does not break the streak, a missed previous scheduled day does.
