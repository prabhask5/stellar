# Decisions

One line of context, the choice, and why. Newest at the bottom of each phase.

## Phase 0 — Scaffold

- **TypeScript version.** TypeScript 7 is the latest release, but `typescript-eslint` only supports `<6.1`. → Pinned TypeScript `~6.0`. Linting with type-aware tooling matters more than the newest compiler.
- **Package manager.** pnpm 12 via Corepack (`packageManager` field). Native build scripts are allow-listed in `pnpm-workspace.yaml`.
- **Internal packages ship TypeScript source.** `packages/*` export `./src/*.ts` directly and are transpiled by Next (`transpilePackages`) and Vite (WXT). No per-package build step, so edits are instant and there is one compiler configuration.
- **Token outputs are committed.** `packages/ui-tokens/css/*.css` and `docs/ios/StellarTokens.swift` are generated by `pnpm tokens` and checked in; a unit test fails when they drift from `tokens.json`. Builds never depend on a generation step.
- **Tailwind names.** `text.primary`/`text.secondary` map to `fg`/`fg-2`, `bg.void` to `void`, `glass.border` to `hairline`, so utilities read naturally (`text-fg-2`, `border-hairline`).
- **Safe-area variables.** Components read `--sat/--sar/--sab/--sal`, which are defined only as `env(safe-area-inset-*)`. Tests simulate a notch or Dynamic Island by adding a class to `<html>` (SPEC §9.1 allows a test-only class). No inset value is hardcoded in components.
- **CSS starfield.** Stars are seeded radial-gradient tiles rendered by a server component: zero client JS, identical on every device, part of first paint.
- **Playwright runs against the standalone build** (the same artefact the Docker image runs), with Chromium using iPhone device descriptors for the phone projects. WebKit is not required to run the suite.

## Phase 1 — Database

- **Local test stack.** SQL parity tests and e2e need a real Supabase. `dev/supabase/docker-compose.yml` runs a lean compatible stack (Postgres 15 + GoTrue + PostgREST + Realtime + pg-meta behind an nginx gateway on :54321) instead of the full Supabase distribution: same APIs, a fraction of the disk and start-up time. Dev-only keys live in `dev/supabase/dev.env`.
- **Idempotent migrations.** Every migration is written so it can be re-run (`create … if not exists`, `create or replace`, `drop … if exists`). That makes the paste-into-Studio fallback safe to run twice and lets the runner, the pg-meta path and the pasted script share one SQL source. SQL is embedded in `bundle.generated.ts` so the standalone server never reads migration files at runtime.
- **`sort_order` is `double precision`.** Reorders write one row with the midpoint of its neighbours; `sp_rebalance` respaces a list when a gap is exhausted. Chosen over text keys because inserts without a rank (API clients) get one from a one-line trigger, and ordering has no collation pitfalls.
- **Timer extras.** `sp_focus_state` adds `phase_total_ms` (the planned length, fixed when a phase starts, so every device draws the same ring even if settings change mid-phase) and `last_completed_phase` / `last_completed_at`. The scheduler compares `last_completed_at` with `notified_phase_end_at` to send each phase-end push exactly once, whichever device advanced the timer.
- **Timer semantics where the spec is silent.** After a long break the round resets to 1. `skip` follows the same auto-start rule as a natural phase end. An advancer up to 10s late starts the next phase exactly at the boundary (no drift); later than that, from "now" (no stale catch-up chain after downtime). `end` and `skip` record an abandoned phase with the time actually spent.
- **Timer state is written only by RPC.** `sp_focus_state` and `sp_focus_sessions` are select-only for the owner; `sp_timer_action` (security definer) is the single writer, so the version check cannot be bypassed.
- **Ledger rule.** Only un-completing something appends negative points. Structural changes (deleting a task, list or routine, rewriting a routine) never touch the ledger: earned stardust is permanent (pillar 3). Two derived awards are reconciled as state: "goal list 100%" and "routine day 100%" are reversed when the state stops being true and are never awarded twice.
- **Goal progress points telescope.** Points are `round(50·new) − round(50·old)`, so one hundred 1% steps earn exactly the same 50 as one jump.
- **Routines hard-delete; tombstones cover delta sync.** Deleting a routine removes its logs (spec). Hard deletes (routines, logs, block sites, quotes) write `sp_tombstones` so `updated_since` can report removed ids. `sp_routines.deleted_at` exists per the spec but is unused. Task/goal/block lists and tasks/goals soft-delete; deleting a list soft-deletes its children with the same timestamp so Undo restores exactly those.
- **Clients compute, Postgres decides.** The web app keeps routines + logs in its cache and uses the shared TypeScript functions for instant rings and streaks; the SQL twins (`sp_routine_days`, `sp_routine_streak`, `sp__scheduled`) serve the API and are held to the same fixtures.
- **Era numbering.** Eras are shown one-based ("Era III · Nebula"), matching the mockup.
- **Quotes.** 132 built-ins, all from authors or translations in the public domain, attributed; commonly misattributed lines were left out.
- **Streak definition.** Consecutive _scheduled_ days completed, counting back from today; an unfinished today does not break the streak, a missed previous scheduled day does.

## Phase 2 — Setup & auth

- **Web session model.** The spec wants httpOnly cookies _and_ direct browser-to-Supabase access. The refresh token lives only in httpOnly cookies (`@supabase/ssr`, cookie name `sp-auth`). The page asks `GET /api/v1/auth/session` for a short-lived access token, keeps it in memory, and uses it for PostgREST and Realtime. Page scripts can never read the long-lived credential, and the PIN endpoint returns no tokens to web clients.
- **Session checks.** The proxy only checks that the session cookie exists (no network on navigation; pages are static shells and RLS guards the data). `/auth/session` verifies the token with the auth server, so "sign out everywhere" and device revocation end other browsers at their next token fetch. An access token already in memory stays valid until it expires (at most one hour); that is inherent to JWTs.
- **Owner only.** The API accepts tokens only for the hidden owner's user id, because the Supabase project may host other users.
- **Lockout is global, not per IP.** There is one owner, so 5 wrong PINs lock sign-in for everyone (30s, doubling, 1h cap, persisted in `/data/lockout.json`; a corrupt file fails closed). A separate in-memory per-IP limiter throttles the auth and setup endpoints.
- **PIN length is never disclosed.** The lock screen shows an Unlock button; after one successful sign-in the device remembers the length locally and auto-submits from then on.
- **Setup endpoints close after first run.** Connect/migrate/verify are open only until setup first completes; afterwards they require a session (Settings → Connection). `RESET_PIN=true` reopens only the PIN step and re-keys the hidden owner, which signs out every device. The PIN is cleared on every boot while the variable is set; the UI and docs say to remove it.
- **Service-role probe.** Checked by fetching a non-existent user id through the admin API (404 = key works) instead of listing users, which is both cheaper and immune to foreign rows that GoTrue cannot scan.
- **VAPID keys** are generated with Node's `crypto` (P-256), with no dependency in the setup path.
- **Data directory.** `/data` in the container, `STELLAR_DATA_DIR` to override, `.data/` beside the app in local development.
- **Migrations on boot** run only when a Postgres connection string is configured; otherwise Settings → Connection offers the paste-and-verify path after an update.
- **E2E isolation.** Tests reset the instance by deleting the files in the test data directory and the owner user, and send a unique `X-Forwarded-For` per test so the rate limiter needs no test-only switch.

## Phase 3 — App shell & design system

- **One cached collection per table.** Each table is a TanStack Query entry holding an array; views (Today, All, Calendar, lists, day rings, streaks) are pure functions from `packages/shared` over those arrays. Realtime patches the arrays by id. Tasks load open tasks plus those completed in the last 90 days; routine logs load the last 400 days.
- **Every write goes through the outbox.** A mutation updates the cache first, then queues an operation (IndexedDB-backed, sent strictly in order). Inserts carry client-generated ids and are sent as "insert or ignore"; updates that waited more than 15 seconds are guarded by `updated_at` so an offline edit cannot overwrite a newer change (last write wins). A rejected operation is dropped, the affected collection is reloaded, and a toast says so.
- **Realtime echoes never fight the user.** While a row has operations queued, incoming Realtime rows for it are ignored; when the last operation settles, the server's version of the row replaces the optimistic one.
- **Realtime joins with the owner's token.** The socket is authenticated (`realtime.setAuth()`) before the channel subscribes, so RLS filters apply. One channel carries all ten tables plus presence (the "N devices in sync" count). Hard-delete tables get an extra unfiltered DELETE listener because delete events cannot be filtered by column.
- **Goal increments are deltas.** `sp_goal_increment` is sent with the delta, not the new total, so increments made offline on two devices add up.
- **Completion feel.** The checkbox fills immediately; the row lingers 600ms, then leaves; consecutive completions share one Undo toast ("3 tasks completed").
- **Routes are static shells.** List detail uses a query parameter (`/tasks?list=…`) rather than a dynamic segment so every page can be precached for offline use.
- **Command bar ordering.** Typed text that matches a command ranks that command first; "Add task “…”" is always offered last (and is the only result for ordinary task text).
- **Emoji data is self-hosted** under `/emoji` (copied from `emojibase-data`), so the picker makes no third-party requests and works offline. Refresh with `node apps/web/scripts/copy-emoji.mjs`.
- **Sidebar wording** follows the mockup: "716 stars to Star Cluster" (the number is stardust still needed for the next era).
- **Dev stack Postgres.** The test stack builds Postgres 15 with `wal2json` and allow-lists it in `output_plugin_libraries` (required by current Postgres releases) so Realtime works locally.

## Phases 4–6 — Tasks, Goals, Routines

- **Quick add defaults.** On the Today tab a new task is due today, on Calendar it takes the selected day, on All it has no date. Otherwise a task added from Today would vanish from the view it was added in.
- **Task lists on phones** are their own segment ("Lists"); on desktop they sit in the right column as in the mockup.
- **"Show completed" is per view and per device** (localStorage). All and list views show what is in the cache (completed within 90 days); Calendar loads older completed tasks for the visible range on demand.
- **Reordering** is available for task lists, goal lists, goals, and tasks inside a list (drag handle, long-press on touch, keyboard). A drop writes one row; `sp_rebalance` runs only when a gap is exhausted.
- **Swipe actions** exist only on touch devices: right completes, left reveals Reschedule and Delete.
- **Goal amounts.** The stepper is −/+ as in the mockup; the current number in "5 / 8 glasses" is itself the tap-to-type control. Holding − or + repeats.
- **Routines: today is always inline on phones** (as in the mockup); tapping another day opens that day in a sheet. Desktop shows the selected day inline beside the calendar. Future days show the schedule read-only.
- **Manage routines** expands in place from the mockup's "Manage routines · N active" row.
- **Tab bar fill** is slightly more opaque than `glass.fill` because Chromium does not blur content that sits inside another backdrop-filtered card; legibility must not depend on the blur.

## Phase 7 — Focus

- **Who advances the timer.** The server's scheduler loop (every 2s, single instance per process, started from `instrumentation.ts`) is authoritative. Each open client also schedules a fallback `advance` 2.5s after the phase should have ended; the versioned RPC makes that race harmless. The loop also runs the daily purge of soft-deleted rows.
- **Optimistic timer.** Controls apply the shared state machine locally (instant), then send the action with the version it was based on. A conflict simply replaces the optimistic state with the server's.
- **Phase strip is a display**, not a control: phases change only through the timer (Start, Skip, End), which keeps every device on the same path.
- **Settings changes apply from the next phase**; the running phase keeps the length it started with (`phase_total_ms`).
- **Space on Focus** starts, pauses or resumes unless a button, field or dialog has the keyboard.
- **Fullscreen** is an in-page overlay that also requests the Fullscreen API where it exists (iPhone has none), so it works everywhere.
- **Block list sites.** Entries are split on whitespace, commas and new lines, so pasted lists work; valid ones are added immediately and only the entries that need fixing stay in the box with a message.
- **Push.** Sent by the scheduler for phases completed by anyone (server or client), exactly once, and skipped if the phase ended more than 10 minutes ago (after downtime). Dead subscriptions (404/410) are removed. Permission is requested only from a button.
- **Stats** come from `sp_focus_stats` (owner time zone); the phase in flight is added client-side so today's total moves while you focus. All focus time counts, including phases ended early; stardust is awarded only for completed focus phases.
